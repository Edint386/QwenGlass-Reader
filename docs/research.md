# 眼镜小说阅读器：调研结论（2026-10-29）

目标：用千问 AI 眼镜 S1 的 Skill 做一个看 TXT 小说的软件——眼镜上界面好看、镜腿滑动翻页、左右侧栏显示状态 / 书名 / 操作；眼镜通过接口拿小说内容和进度；电脑端读 TXT、回传内容、记录进度。

依据：千问 AI 硬件开放平台官方文档（下称"文档 §N"）、glasscast 投屏项目在**同一块真机**上测出来的结论（glasscast 仓库的 `docs/research.md`，下称"投屏 §N"），以及本次在本地 WASM 模拟器里跑通的原型（§6）。标【真机待验证】的条目还没在眼镜上跑过。

## 0. 结论

1. **翻页不能经过大模型**。每次工具调用都要过模型（秒级），工具还有 3 s 超时、跨境链路经常超时（投屏 §9.9）。翻页必须在眼镜页面里本地完成。
2. **页面自己发不了 API 请求**。Waft-DSL "不直接 fire HTTP / RPC"（文档 §33 §5），页面里唯一能主动访问网络的是远程图片 / GIF / 帧合集的下载。所以推荐方案把**正文做成电脑端渲染的页图**：滑一下 → 页面里一个计数器加一 → 图片地址变化 → 手机替眼镜下载新的一页。电脑端从请求地址就知道用户翻到了哪一页，**进度天然被记录**，不需要另一条回传通道。
3. 两侧栏、菜单、高亮框用**原生控件**，按键立即响应，不产生网络请求；正文页图里带章节名、百分比、页码和进度条。
4. 这套方案用到的机制都已在真机上验证过（图片按地址后缀加载、换图约 1 张/秒、`data://` 改计数），**不需要白名单、不需要发布插件**就能真机测试。翻页延迟预计约 0.7～1 s（家里局域网），在外经公网约 1～1.7 s。
5. 本次在模拟器里跑通了完整原型：TXT → 分章 → 分页（禁则、悬挂标点、两端对齐）→ 4 级灰度 PNG（每页约 9 KB）→ 页面翻页 / 菜单跳章 / 改字号 → 电脑端按字符偏移记进度（§6）。
6. 想要"原生文字、瞬间翻页"，有两条升级路线（§3 方案 B、C），都卡在没验证或要白名单的环节上，列进 §7 的真机探针。

## 1. 平台约束（决定方案的硬条件）

| # | 约束 | 出处 | 对阅读器的影响 |
|---|---|---|---|
| 1 | 页面不能发 HTTP 拿 JSON；能联网的只有 `<image>` / `<gif>` / `<frame-set>` 的远程资源 | 文档 §33 §5、§36 §9 | 正文只能是图片，或在打开页面时一次性放进 dataSource |
| 2 | 页面数据只有三个来源：打开时的 dataSource、页面内 `data://`（只能写标量）、Agent 推送的 `SHOW_UI UPDATE` | 文档 §34 §4、§18 | 纯 Skill 下，换内容要么换图片地址，要么让模型重新打开页面 |
| 3 | 打开页面要由模型调 `ui_page_render`，dataSource 是模型从工具返回值里照抄的；`ui_schema.json` 的 Hook 在真机上看不到 MCP 的结构化出参（只有 `content[0].text`），条件不命中 | 投屏 §9.5 | dataSource 只放三个短字段（地址前缀、书名、显示设置），让模型抄得又快又准 |
| 4 | 工具 3000 ms 超时；平台在大陆、服务器在境外，第一次调用常超时，要"超时立刻原参数重试一次" | 文档 §40、投屏 §9.9 | 打开书、跳章这类偶发操作可以走模型；翻页不行 |
| 5 | 真机远程图由 iPhone「千问AI穿戴」App 下载再经蓝牙送到眼镜：每个文件约 0.65 s 固定开销；换图快于约每 0.7 s 一张就一张都显示不出来；地址必须以图片后缀结尾（`?ts=` 查询串下载成功但不显示） | 投屏 §9.6、§9.18～9.20、§9.25 | 翻页约 1 s 一页，阅读够用；快速连滑时只显示最后一页（位置仍然正确，见 §4.2） |
| 6 | 远程图解码预算 742 400 B；640×290 整屏图真机不显示，600×272、480×218 能显示；2.5～10 KB 都显示过 | 投屏 §9.7 | 正文图 478×290（解码 554 KB），4 级灰度 PNG 约 9 KB（最大 10 KB） |
| 7 | 内核按完整 URL 缓存远程下载，跨页面有效；真机每次绑定刷新都会让还没加载完的图重新加载 | 投屏 §9.2 E7、§9.13 | 地址里带会话号；电脑端对重复请求必须幂等（§4.2） |
| 8 | `data` 只存小整数（真机超过 2147483647 会被卡住）；`data://update` 写多个键用 `&amp;` 分隔，`on-key-*` 和 `<event action>` 在内核 v0.2.11、官方预览和真机都写全了（早先 `frame-set` 的 `on-completed` 只生效第一个） | 投屏 §9.11、§9.2 E4 | 每个操作只写一个计数器 |
| 9 | 表达式：在**第一个运算符处切成两段**，每段先查变量，查不到用 atoi，`+ - * /` 都算，整数运算，除数为 0 得 0。所以 `{{d:x * 36 - 36}}` 得 `x*36`（右段 atoi 得 36），`{{d:x + 1 + 1}}` 得 `x+1`，`{{36 * d:x - 36}}` 右段查不到得 0；常量在左本身可算，文字版的 `{{100 - s.b}}`、`{{d:lv / 10}}` 就靠这两条（2026-11-01 反汇编 v0.2.11，未在内核上实跑）。比较式三元结果不可靠。比较写不了小于号：XML 里只能转义，模拟器里 `{{fs &lt; 24}}` 在 fs = 16 时不成立，要写成 `{{24 > fs}}`（2026-11-01 实测） | 本次模拟器实测 `img/probe-arith.png`；投屏 §9.13、§9.2 E10 | 页面里算不出百分比，进度显示放进页图；高亮框用固定位置 + `a:if` |
| 10 | 按键只有 `on-key-enter/back/prev/next/home`；S1 手势：单击 = enter，双击 = back（默认退出页面），前滑 / 后滑 = prev / next | 文档 §33 §8.5、§36 §4.10；模拟器按键表 | 见 §4.3。模拟器和官方预览的按键面板把 `on-key-prev` 标成前滑，页面提示和系统提示图标（`res://prompt/slide-forward`）都写前滑下一页。2026-10-31 真机用下来页面提示没有问题，判断方向看真机，别看面板 |
| 11 | `scroll-view` / `markdown-view` / `recycle-view` 默认进焦点链，会吃掉上下键用来滚动 | 文档 §36 §12 | 阅读页不用这些组件，按键全部交给页面级 `<key-event>` |
| 12 | 屏幕是 640×290 单色绿光机：黑 = 不发光，颜色只表现为亮度；字号只有固定档位 | 文档 §34 §3、投屏 §9.2 E6 | 黑底亮字；正文用电脑端字体渲染，不受字号档位限制 |
| 13 | 每个节点直接子元素 ≤ 64、页面绑定 ≤ 128、`<tick>` ≤ 4，其余上限见 §10.1 | 文档 §35 §6、投屏 §9.8、§10.1 | 阅读页 42 个根子元素，余 22 个 |

## 2. 需求怎么落到平台上

| 需求 | 做法 |
|---|---|
| 眼镜上好看的 UI | 正文由电脑端排版渲染（字体、行距、禁则、悬挂标点、两端对齐都可控）；两侧栏和菜单用原生控件（清晰、零延迟）。截图见 §4.4 |
| 适配镜腿滑动 | 页面级 `<key-event>`：前后滑翻页、单击开菜单、菜单里滑动选择、单击确定、双击退出 |
| 左右侧栏 | 左：书名竖排 + 时间 + 连接状态；右：操作提示（阅读时）/ 菜单操作提示（菜单时） |
| 眼镜通过 API 拿小说 / 进度 | 翻页：页图地址就是 API（`GET …/r/<书>/<会话>/<计数>.png`）。打开书、跳章、查进度：语音 → 模型 → MCP 工具 |
| 电脑端读 TXT、回传、记进度 | 电脑端服务扫描书库目录、解码切章分页、按请求渲染页图；进度按字符偏移存 JSON（换字号后仍落在同一段） |

## 3. 三种方案比较

| | **A. 页图（推荐）** | B. 原生文字分段下发 | C. Agent 自定义接入 |
|---|---|---|---|
| 正文怎么到眼镜 | 页面换图片地址，手机下载电脑端渲染的页图 | 一次把约 10 页文字放进 dataSource，页面本地翻；翻完再让模型重新打开 | 自己的 WebSocket 服务推 `SHOW_UI`，收 `UI_ACTION`（镜腿事件） |
| 翻页延迟 | 约 0.7～1.7 s | 段内瞬间；每约 10 页停 3～6 s 等模型 | 每页一次云端往返（约 0.5～1.5 s，未测）；可与 B 混用做段内本地翻页 |
| 文字效果 | 电脑端字体，排版完全可控 | 眼镜原生字体，固定字号档位 | 同 B |
| 进度记录 | 页图请求本身就是进度 | 段内翻页电脑端不知道，需要另做信标图 | 服务端天然知道 |
| 前置条件 | 无（全部机制真机已验证） | 要验证：OpenAPI 工具 + Hook 能否把结构化出参交给页面；`svc://ui-action?mode=agent` 在普通 Skill 里能否触发模型 | 自定义接入白名单（联系运营）、公网 wss、插件和关联技能由用户本人发布、S1 固件 ≥ 1.11.5 |
| 主要风险 | 翻页要等约 1 s；断网时翻不了页 | 两个未验证环节；模型要正确地重新打开页面 | 白名单和发布流程；内测功能 |

建议：**先做 A**；电脑端的书库、切章、分页、进度这一层写成与传输无关的核心，B / C 以后只是在上面加一个"输出 JSON 段落"或"WebSocket 推送"的适配层。

## 4. 推荐方案（A）设计

### 4.1 链路

```
 语音「看小说 / 继续看《雾港来信》/ 跳到第三章」
        │
        ▼
 千问模型 ──调用──► reader MCP 工具（open_book / jump / list_books / reading_status）
        │                         │  返回 {"u": "https://…/r/<key>/<书>/<会话>", "t": "书名", "s": 显示设置, …}
        ▼                         │
 ui_page_render(templateName="reader", dataSource={"u", "t", "s"})   ◄── 模型照抄 u、t、s
        │
        ▼
 眼镜 reader 页面 ── 镜腿滑动 ──► data://update?a=… ──► <image src="{{u}}/a-b-j-k-z-….png">
        │                                                   │
        │                              iPhone 千问AI穿戴 App 下载（经公网隧道 / 家里局域网直连）
        │                                                   ▼
        └──────────── 显示页图 ◄──────────── Mac 上的 reader 服务：按计数差值移动位置、记进度、渲染 PNG
```

### 4.2 页图地址协议（已在模拟器跑通）

```
GET {u}/{a}-{b}-{j}-{k}-{z}-{uf}-{uw}-{ub}-{us}.png
u = https://<公网域名>/r/<随机 key>/<书 id>/<会话号>     ← open_book 每次生成新会话号
a 下一页次数  b 上一页次数  j 下一章次数  k 上一章次数  z 自动翻页次数
uf 字号  uw 粗细  ub 亮度  us 行距（0 = 这次打开还没改过）
```

- 前五段是**只增不减的累计计数**，页面每个操作只给其中一个加一（约束 8）；后四段是设置的绝对值（§5）。段数不是九的是还开着的旧页面，按旧顺序 `a-b-j-k-f-g-z` 只取翻页用的几段。
- 电脑端记住每个会话上次看到的计数，按**差值**移动阅读位置：先改字号、再跳章、最后翻页，然后返回当前页的图片。
- 为什么用累计计数而不是"命令 + 序号"：
  - 内核会重复请求同一地址（首屏连发 3 次、绑定刷新打断加载时重发，约束 7）：差值为 0，位置不动。
  - 快速连滑时中间某个地址可能根本没发出去：下一个地址里的计数已经包含了它，位置仍然对。
  - 页面不需要知道自己在第几页，跳章、改字号后页码由电脑端重新算，页面状态不会和电脑端对不上。
- 会话的第一次请求只记基线、不移动：模型重新打开页面（同一页面 `on-new-intent`）时 `<data>` 计数不归零，换了新会话号也不会被当成几十次翻页。
- 地址里的随机 key 做鉴权（眼镜发不了请求头，同 glasscast）：key 不对、书不存在、地址不合法一律同样的 404，访问日志里 key 打码。
- 后缀写 `.jpg` 时电脑端返回 JPEG，作为真机不显示 PNG 时的退路（探针 P1）。文字页用 JPEG 不划算：q40 约 21 KB，是 PNG 的两倍多。

### 4.3 交互映射

| 状态 | 前滑 / 后滑 | 单击 | 双击 |
|---|---|---|---|
| 阅读 | 下一页 / 上一页（`a`、`b` 加一） | 打开菜单 | 系统默认：退出页面（进度已在电脑端） |
| 菜单 | 上下移动选中项（首尾相接） | 执行：返回阅读 / 自动翻页 / 下一章 / 上一章 / 显示设置；返回和换章执行后关菜单。自动翻页关着时这一项进设置，开着时显示“停止自动翻页”，单击直接停止并回到阅读 | 同上 |
| 自动翻页设置 | 前滑加 1 秒、后滑减 1 秒（1～30 秒，默认 7 秒，减到 1 以下显示“关闭”，此时单击不开启、回到阅读） | 确定并回到阅读 | 同上 |
| 显示设置菜单 | 移动选中项：字号、粗细、亮度、行距、返回，每项后面是当前值 | 进入这一项；“返回”回到主菜单 | 同上 |
| 调某一项 | 前滑增大、后滑减小，右栏中间显示当前值。字号、粗细、行距每滑一下就换页图，连续滑动时停手后显示最后一张；亮度是本地遮罩，立刻变 | 保存亮度并回到显示设置菜单 | 同上 |
| 任意 | 语音「跳到第 N 章」「回到开头」「换一本」「我看到哪了」 → 模型调工具 → 重新打开页面 | | |

实现要点（`pages/reader/template.xml`）：

- 菜单状态只用一个变量 `m`：0 = 阅读，1～5 = 主菜单，11～15 = 显示设置菜单，21～24 = 调字号、粗细、亮度、行距，25 = 自动翻页设置。条件全写成"变量 运算符 常量"（约束 9）。
- 按键只有一条 `<key-event>` 条件链，按状态分支，一个元素同时写单击、前滑、后滑（§10.2）。动作和关菜单写在同一次 `data://update` 里，所以不会出现“关了又开”。
- 菜单里移动选中项不改图片地址，不产生网络请求，只是原生控件重绘。
- 自动翻页的计时放在页面里，步数存在事件参数里倒数（投屏 §9.19 的探针五）：`<tick>` 只有秒、分两档且会刷新绑定，data 每写一次都可能打断图片加载，不用 tick 是因为它打开页面就一直刷新，没法随开随关。真机实测每步约 12 ms，所以 84 步约一秒；每走完一秒写一次 `c`（这一页还剩几秒），左栏显示“N 秒后翻页”（原生字号只有固定档位，15 会退回 14，所以用 14 号），到点把 `c` 和 `z` 一起写。关闭时循环不运行，页面不刷新；开启时的耗电未测。手动翻页在同一次写入里把 `c` 写回整页时长并改图片地址，菜单打开时倒计时停住、左栏显示“自动翻页 / 已暂停”，关菜单后重新计时；页面被遮挡、灭屏、摘下眼镜时关闭。`z` 的差值再大也只翻一页。新图加载约 1 秒，这期间用户看到的还是旧页，所以服务端把 1.5 秒内先后到达的一次自动翻页和一次手动“下一页”算成同一次（`TURN_MERGE_SECONDS`），连续手动翻页不受影响。
- 亮度：整屏最上面盖一层黑色，`bg-opa` 绑定 `d:op`，亮度每档差 10%、透明度差 25，正文、书名、操作栏、时间和菜单一起变暗，调的时候不用换页图。`<data>` 的属性不解析绑定，所以打开页面时用 `on-load` 把 dataSource 的 `s` 写进 `d:`；`s` 由大模型照抄，漏传时留默认值（全亮），没保存的项不会发给电脑端。
- `animate-alpha` 结束后值能保持，但 `a:if` 只是显隐，模拟器里切换后动画不会重新开始，所以不用它做“过一会变暗”。
- 数据写入和图片加载的关系（模拟器，图片 2.5 秒才返回，5/10/15 秒的累计请求）：不刷新 2/3/3；每秒写数据 2/4/5，写的键没有任何绑定也一样；`<tick>` 每秒刷新 2/4/5；`refresh="minute"` 2/4/4，但这种模式下读到的 `tick:` 值停在上次刷新时，不能当秒表。只有 `src` 里带绑定的图才会重新请求。结论：图加载完之后写一次没有代价，图没加载完时任何写入都会让它重来。
- 不禁止返回键（`forbidden="back"`）：真机上 `waft://app/exit-page` 的可靠性没验证过（投屏 §9.17），保留系统双击退出最稳。

设计取舍：

- **黑底亮字**：光机黑色不发光，大面积亮色在眼镜上是一整块亮绿（投屏 §9.20）。正文灰度 235、辅助信息 120、线条 60。正文再描粗 0.08 px、字边半透明像素乘 1.3 再量化，24 号的满亮像素从 44% 到 60% 以上，页眉页脚不变（§5）。
- **黑体而非宋体**：宋体的细横在绿色光机上可能发虚（还没在真机上对比）；Hiragino Sans GB W3 笔画均匀（对比图见 §5）。字体、字号、行距都在电脑端，可随时换。
- **进度放在页图里**：服务端掌握位置，页面算不出百分比（约束 9）。侧栏只放不随翻页变化的书名和本地就能拿到的状态。
- `theme="no-status-bar|disable-chat-bar"`、`screen-awake="keep"`：沉浸式全屏、阅读时不熄屏（`keep` 真机未验证，投屏 §8-5）。
- 不用 `<tick>` 刷新时钟：真机上图片没加载完时每次绑定刷新都会重新加载它（约束 7）。时间随每次翻页刷新，阅读时足够准。
- 可选打磨【真机待验证】：两侧栏加 `display-z="far1"`，让正文在立体视觉上更靠前（文档 §35 §3）。

### 4.5 进度

- 电脑端每次位置变化就写 `progress.json`（原子替换）：书 id → 字符偏移、字号、本章页码 / 本章页数、章节名、百分比、更新时间。
- 用**字符偏移**而不是页码保存：换字号或改版式后重新分页，仍然落在同一段文字上（模拟器验证：24 → 28 号，第二章第 1/4 页 → 同一段文字所在的第 1/5 页）。
- 只有真的移动了才写（重复请求不写）。
- 页图版和 Agent 文字版是两个进程，共用这个文件：读的时候发现文件换过（inode、修改时间）就重新读；写的时候加文件锁，先读最新内容再改自己这一项，所以不会互相覆盖。
- 文件坏了不清零：先用内存里的进度和备份 `progress.json.bak`（每次写入都更新，是一份真实的拷贝，书取更新时间新的那份，显示设置取备份。闲着的实例内存是旧的，刚重启的实例内存是空的，只靠内存会把另一个实例的新进度盖回去），下次保存时把坏文件抄成 `progress.json.corrupt-时间`，别的书的进度还能手工救回来。只抄不挪，坏文件留到新文件原子替换它：挪走之后到写好之前没有文件，另一个实例这时读到的是“从头开始”，翻一页就把位置写回书头。写不进去（磁盘满、没权限）只记日志，翻页不断。一条记录里的偏移或时间戳不是数字，按没读过算。
- 语音"我看到哪了"→ `reading_status` 工具直接读这个文件。

### 4.6 MCP 工具与 SKILL.md（`glassreader/mcp_tools.py`、`skill/SKILL.md`）

| 工具 | 入参 | 返回 | 说明 |
|---|---|---|---|
| `list_books` | `query`（可空） | 书名、读到的章节、百分比、最后阅读时间（最近读的在前，最多 20 本） | "书架里有什么" |
| `open_book` | `title`（可空 = 最近读的那本；书名号可有可无，完全相同 > 开头相同 > 包含） | `u`、`t`、章节、本章页码、百分比、字号 | 每次生成新会话号；记一次"最近阅读" |
| `jump` | `title`、`chapter`（“第三章”“3”“夜渡”“下一章”“上一章”）/ `percent` / `pages` | 同 `open_book` | 模型随后用新的 `u` 重新打开页面 |
| `reading_status` | `title`（可空） | 书名、章节、本章页码、百分比、最后阅读时间 | 不打开页面 |

- 返回体都是扁平 JSON，`message` 是可以直接念的一句话（"已打开《雾港来信》，第二章 第一封信""书架上没有找到《三体》，有：…"），技术细节在 `error`。
- 参数按宽松类型收：章节号传整数、百分比传 `"50%"` 都行（大模型常这样传）。
- 本机实测（无状态 `tools/call`，不先 `initialize`，同平台「无状态协议」）：每次 14～76 ms。

SKILL.md 要点（沿用 glasscast 已验证的写法）：

1. 用户想看小说 / 继续看 / 换书 / 跳章：先调工具，成功后**必须**调 `UI页面渲染(templateName="reader", dataSource={"u": <返回的 u>, "t": <返回的 t>, "s": <返回的 s>})`，三个字段逐字照抄。
2. 工具返回"工具调用失败 / 工具执行失败 / MCP 工具执行超时"时，不说话、原参数立刻重试一次（投屏 §9.9）。
3. 不要朗读正文；只播报一句"已打开《…》第 N 章"。（以后可加"读给我听"：工具返回当前页文字，由模型播报。）
4. 页面打开后翻页、菜单都在眼镜上完成，不需要模型参与。

### 4.7 网络与部署（复用 glasscast 的基础设施）

- 平台访问 MCP、手机下载页图都需要公网 HTTPS。现成的入口是 `cast.example.com`（公网服务器上的 1Panel OpenResty → 反向 SSH 隧道 → Mac），家里还有路由器把这个域名解析到 Mac 的局域网直连（投屏 §9.14，取图约 15 ms，经公网约 0.7 s）。
- 建议**同一域名按路径分流**：`/r/` 和 reader 的 MCP 路径转给 reader 服务，不新建域名和证书。需要改服务器上的 OpenResty 配置、隧道多转一个端口、`lan_https_proxy.py` 按路径分流——**改远程服务器前要你点头**。
- MCP 插件用「无状态协议」，每次调用一个 POST（投屏 §9.9 验证过能减少超时）。服务端按章、按需分页，几 MB 的长篇第一次打开也在 1 s 内（测试覆盖）。
- 服务可以挂在路径前缀下：`READER_PUBLIC_URL=https://cast.example.com/reader`，反代剥掉 `/reader` 后转发，服务本身的路由是 `/r/…`、`/mcp`、`/healthz`。

## 5. 电脑端设计（`glassreader/book.py`、`pager.py`、`library.py`）

| 环节 | 做法 |
|---|---|
| 解码 | BOM（UTF-8 / UTF-16）→ UTF-8 → GB18030（国内 TXT 大多是 GBK）。UTF-8 里只有个别坏字节时（下载截断）还按 UTF-8，不让整本变乱码 |
| 切章 | 正则匹配独占一行的「第…章 / 节 / 回 / 卷 / 集 / 部 / 篇」「序章 / 楔子 / 尾声 / 后记 / 番外…」，标题 ≤ 30 字；第一章前有内容就归为「前言」；一章都匹配不到就整本作为一章。宽松写法（第、数字、章之间有空白，章字后面直接接标题，前面带“正文”，大写 CHAPTER，第 N 话）比规范标题多出一倍才用来分章，一个规范标题都没有时至少要 3 行，这种标题行留在正文里；超过 5 万字的章节按段落切开，标题加序号。这两条只改章节划分，全书的字符偏移不变。切开的章节，“下一章”“上一章”和页面上的 j、k 按切开后的段走：没认出标题的书全书是一章，不这样就没法按章跳。序号只用来排版，念给用户的句子和工具返回的 chapter 都不带 |
| 段落 | 按行切段，去掉首尾空白和全角空格，段首统一缩进两格 |
| 断行 | 按实际字体逐字量宽度贪心断行；行首禁则字符（`，。、；：？！）》」』…—”` 等）悬挂到上一行行尾，最多两个；行尾禁则字符（`（《「『“` 等）推到下一行 |
| 对齐 | 非段末行逐字画、把剩余宽度均分到字间，右边缘齐整 |
| 分页 | 每页固定行数（24 px：7 行，约 110 字），章节从新页开始。**按章、按需分页**：几 MB 的长篇全书分页要好几秒，工具只给 3 s；所以页脚页码是“本章第几页”，全书位置看百分比和进度条 |
| 渲染 | 灰度画布 → 量化到 4 级灰度 → PNG。24 px 每页中位 8.4 KB、最大 9.3 KB，16 px 中位 7.6 KB、最大 11.5 KB，单页渲染约 13 ms（不量化约 24 KB、8 级约 12 KB、JPEG q40 约 21 KB） |
| 笔画 | `TEXT_STROKE` 0.08 px + `TEXT_GAIN` 1.3，用 Noto Sans CJK 在模拟绿色下对比过：描粗到 0.12 时 16、18 号的密字开始糊。真机效果还没对比。字符落点不用取整：Pillow 已经按整数像素画，取整前后输出完全相同；纯单色渲染笔画粗细不匀，不用 |
| 字号 | 16～32，每档差 2，每本书各记各的。16 号每页 10 行、每行 28 字 |
| 显示设置 | 粗细 6 档（默认第 3 档）、亮度 100%～10%（每档差 10）、行距 125%～185%（每档差 15，默认 140%）。全局一份，存在进度文件的 `_display` 键下，换书不用重调。文字版智能翻页的速度存在 `_text` 键下，页图版不用这个值。保存时只写改动的几项，别的键都留着，`_display` 里不认识的键也一样。档位都是等差的，页面上直接加减，不用查表 |
| 设置值 | 图片地址最后四段是字号、粗细、亮度、行距，0 = 这次打开还没改过。这几段是绝对值，页面重开也不清零，所以按会话比较：某一段相对上次变了才用，会话的第一次请求只记基线，不然文字版刚改的设置会被地址里的旧值改回去。字号、粗细、行距滑动时就写，亮度单击保存时才写。亮度面板只能单击退出，没调也会写，所以亮度段从 0 变成页面打开时的值不算改动；调过之后再调回这个值算改动 |
| 书名 | 左栏 72×176 的小图，约 1 KB。短书名 24 号一列；长的缩小到 20～14 号排两列，“书名 - 作者”各占一列，放不下才省略。原生控件算不出字数，也拆不了列 |
| 缓存 | 字宽按字号缓存（逐字量宽度是分页的主要开销）；分页按（书、章、字号）缓存；页图按（书、字号、章、页）缓存；书文件改了（mtime 变）自动重新解析；内存里只留最近用的两本书（容器只有 256 MB），放掉书时连分页和页图缓存一起清 |
| 跨章 | 翻过本章最后一页进入下一章第一页，往前翻到上一章最后一页；只有标题没有正文的章节跳过；书头书尾停住，已在最后一章时“下一章”不动，不退回本章开头 |
| 书库 | 递归收集 `*.txt`，扩展名不分大小写（跳过隐藏目录）；书 id = 相对路径的哈希，改名会被当成新书 |

## 8. 风险与注意

- **版权**：只给自己看自己的 TXT；技能发布选「个人私有」，不上技能广场。
- **隐私**：页图会经过公网入口；地址带随机 key，1Panel 默认访问日志会记下 key（投屏 §9.9 附带发现），上线前关掉或换 key。

- **电量**：常亮 + 每页一次蓝牙传图；必要时去掉 `screen-awake="keep"`。
- **平台操作**：不发布、不碰已有的插件和技能；新建的都是草稿，发布由你来做。

### 10.2 写法经验

- **一次写多个键**：`data://update?c={{d:p}}&amp;a={{d:a + 1}}` 两个键都写入，值里可以有 `{{d:a + 1}}`。文档 §36 §10.3 就是这样写的，内核 v0.2.11、官方预览、真机都成立，平台保存校验也接受。
- **旧规则为什么错了**：“每次只写一个键”来自投屏 §9.2 E4，当时测的是 `frame-set` 的 `on-completed`，后来被当成所有动作的规则，页面因此多占了二十多个根节点名额。记结论时要写清测的是哪个属性、哪个内核，换个地方用之前再测一次。
- **一条按键链**：一个 `<key-event>` 可以同时写 `on-key-enter`、`on-key-next`、`on-key-prev`，放在 `a:if` / `a:elif` / `a:else` 链里按状态分支。链是按键分开算的：某一支缺了哪个键，这个键就落到下一支，所以每支都要写全。特殊状态（如 `m == 23`）要排在 `m > 20` 前面。
- **事件也写成一条链**：`event://auto?` 用 `a:if` / `a:else` 按 `p` 定去向。拆开写时先清 `p` 会让下一条误入设置。
- **布局属性的绑定每次写数据都重新设置**：写数据时内核只刷新依赖这个键的绑定，但 `width="{{x}}"` 这类例外，和写了什么键无关，`a:if` 隐藏的分支也算。文字版每槽一条进度条时，菜单移动一格刷新 9 个绑定，页图版 1 个；固定 `width` 后回到 1 个，固定 `text`、`font-size`、`font-weight` 没有变化（模拟器的 `bindings applied` 日志）。改成全页一条后是 2 个。重复的元素上不要绑定布局属性。真机上的改善幅度没有量过，模拟器的耗时波动太大。
- **绕服务端一圈约 2 秒，能在页面做的就在页面做**：文字版调粗细时服务端约 1 毫秒、下发 255 字节，用户仍要等约 2 秒。控制台日志里从 `UI 操作` 到 `屏显` 通常 0.44 秒，有时约 1.05、1.7 秒，翻页也一样；剩下的时间在眼镜、手机这段和重绘上，日志看不到。0.44 秒的底数基本是网络。语音还要加上识别的时间，平台只发整句结果（`UTTERANCE`），没有中间结果可以抢先处理。亮度一直在本地改，所以不卡。字号、粗细改成绑定 `d:` 变量后，滑动时立刻生效，单击保存才上报。
- **原生字体的行距要量，不能按字号估**：字号 16、18、20、22、24、28、32 的行距是 23、26、29、32、35、41、46 像素，约 1.44 倍。原来按 1.32 倍估，16、20、22 号每页多排一行，最后一行被切掉只剩上半截，下一页又接着往后排，这一行就漏了。真机上 20 号压到进度条，和这个结果对得上。量法：模拟器里画一个多行 `label`，从画布读每行的像素范围。字宽没有这个问题，全角约等于字号，`n` 约 0.6 倍，粗体和常规一样宽。
- **灰度低于约 30 屏幕就不发光，暗色字更早“被侵蚀”**：2026-11-01 用户逐档报告，和灰度对得上。原来遮罩每档差 25 且全屏一样：章节名（灰度 122）在亮度 40% 时只剩 50，缺四分之一；20% 时 26，看不见；菜单边框（90）30% 时 28，消失；分割线（42）60% 时 25，消失；正文（232）20% 时 50，笔画里有黑点，10% 时 27，看不见；只有白色粗体大字（255）10% 时 30 还在。细笔画的边缘是半透明像素，灰度到 70 左右就开始缺。现在遮罩按档位算：正文和书名每档 22，外圈每档 15；时间、进度条、提示文字压到和章节名差不多，避免低亮度时比正文还亮。亮度 10% 时正文 51，次要内容 57～64，线条 32。用户觉得更亮的那一档不够暗时，先看是不是外圈的字太亮。表达式只认整数：`* 0.5` 得 0，`/ 2` 可以，超出 0～255 会回绕。
- **`opa` 代替遮罩试过，又改回来了**：写在容器上的 `opa` 会传给子元素，图片也一样，模拟器里亮度和遮罩基本相同（亮度 40 时正文最亮值 92 对 95），但 2026-11-01 上真机后用户觉得效果不好。整页一个 `opa` 还会让菜单的黑底变透明，要分层写，多 8 个绑定。
- **双击二次确认用 `confirm-back-text`，不要写 `forbidden="back"`**：`forbidden` 会让内核直接吞掉返回键，真机双击没反应，`on-key-back` 也不触发，文档的说法不对。`confirm-back-text` 单独写才生效：第一次返回只显示这句话，第二次触发 `on-key-back` 并关页面。提示显示在 `prompt-config` 的位置，页面里要有 `<prompt-config text="" />`，主题带 `disable-chat-bar` 也能显示。内核字符串里能看到这段逻辑（`confirm-back: showing prompt`）。
- **页面和服务都要改的值放主数据**：`data://` 只写 `d:`，服务写不到；`dataSource://update?fs=28` 写主数据（`S` 大写，文档 §10.3.1），服务的 UPDATE 也写这里。字号这样放，滑动时本地立刻生效，语音改字号也不用重开页面。
- **字重可以写数字**：`font-weight` 接受 100～900，700 起是粗体。28、32 只有粗体字模，写常规显示的也是粗体。`{{d:m > 20 ? d:fv : fs}}` 这样的三元绑定写在 `font-size` 上字号不对，平台文档两处对三元的说法也相反，不要用。
- **能用但没用上**：`<event>`、`<key-event>`、`<lifecycle-event>` 放在子 `view` 里也能触发，`a:if` 隐藏时也一样。文档写只能放根节点，所以只当后手。
- **可以查表**：`{{nx[d:i].n}}` 这样按变量取数组元素，在 URI、`text`、`top` 里都能用，主数据的变量也能当下标（`{{up[fs].n}}`），变量一变就刷新。详见 §11.11。
- **不起作用**：`on-key-*` 写在 `view` 上（没有焦点）；表达式里的 `%`；条件里的 `&amp;&amp;`（只算第一个比较）；`<data>` 属性里的绑定。

### 10.4 验证方法

- **模拟器和官方预览是同一个内核**：控制台的包是 0.0.38，本地是 0.0.34，但 wasm 完全相同（sha256 前缀 `6b48dec853f0f08c`，v0.2.11）。
- **官方预览只运行已保存的文件**：编辑器里没保存的内容和“刷新”都不算。不想动草稿时，在预览页面拿到内核模块，用 `module.ccall('wasm_test_open_dsl', null, ['string','string','string'], [xml, dataJson, uri])` 注入。注入前先调 `wasm_test_close_page`，否则官方自己的页面也在跑，每个事件响应两次。
- **网页预览的局限**：不请求页图，只能看页面逻辑和写入的值；平台保存校验和真机都要另外验证。
- **保存到平台**：脚本改编辑器时，等“保存”可用再点，点到禁用的按钮不会有任何提示。保存后刷新页面，用 sha256 和本地文件比对。
- **下发到真机**：保存后的页面不用重新下发，但要退出再打开才会用上。
- **改地址格式时的部署顺序**：先服务器，后平台页面和 SKILL.md。新页面配旧服务器时，`z` 那一段会被读成字号。
- **2026-10-31 真机结果**：精简版的翻页、菜单、显示设置、自动翻页都正常。

### 10.5 自动翻页卡死（还没修）

- **服务端没问题**：821 个图片请求全部 200，渲染最慢 99 ms，没有重启和内存溢出，客户端地址也没变。
- **触发**：眼镜到服务器之间停 12～39 秒，没有任何请求，恢复后一批请求同时到。是蓝牙还是手机 App 还不知道。
- **为什么拖得久**：每秒写 `c` 会打断没加载完的图（§4.3 的数据），同一地址被请求 6～15 次。加载本身接近 1 秒，每秒一次写入没有余量。计时也不停，用户没看到的页被翻了过去。
- **`<tick>` 解决不了**：§4.3 的数据里，每秒 `tick` 和每秒写数据的结果一样。探针要有不刷新的基线，图片的 `src` 要带绑定，否则测不出差别。
- **候选做法**：只在最后 3 秒显示倒计时；不显示秒数；用小 GIF 倒计时（探针 8 重启过眼镜，有风险）。服务端还可以合并成批到达的自动翻页。精简版没有改这部分。

## 11. Agent 版的听书和真机记录（2026-11-01）

### 11.1 平台能提供什么

- **只能播文字：** `SPEAK` 只收纯文字，没有声音、语速、SSML 参数。第三方发不了音频到眼镜，页面也没有音频控件。
- **没有播放回执：** 文档写明 `hasNext=false` 只表示文字发完，不表示播完。页面的 `ctx:` 是固定字段，内核也没有播报状态可读。服务不知道读到哪，只能按语速估。
- **能做的：** 同一个 `speechId` 连续发分片，`STOP_OUTPUT` 随时停。
- **做不到的：** 插入静音。分片里的换行也不产生停顿，真机上试过。
- **不走 RTC：** 插件的通信方式是“ASR文本”，服务只收发文字。
- **没做的路线：** 服务端生成音频、手机播放、眼镜当蓝牙耳机。声音和语速都能选，但眼镜能不能当蓝牙音箱没验证，语音合成可能要付费。

### 11.2 朗读节奏是怎么调出来的

| 版本 | 每秒字数 | 分段 | 提前发下一段 | 页面提前 | 真机结果 |
|---|---|---|---|---|---|
| 1 | 4.5 | 至少 60 字，到句末 | 2 秒 | 0 | 每一两句停一下，翻页晚 |
| 2 | 5.5 | 至少 40 字，到句末 | 6 秒 | 2 秒 | 几句停约 1 秒，翻页晚 4～5 秒 |
| 3 | 6.0 | 段落凑够 40 字 | 4 秒 | 4 秒 | 用户要求不凑字数 |
| 4 | 6.6 | 每段一次 | 4 秒 | 4 秒 | 第一页准，第二、三页早半句，段落之间没有间隔 |
| 5 | 6.8 | 每段一次 | 0 | 1 秒 | 段落间几乎没有空隙，翻页略早几个字 |
| 6 | 6.5 | 每段一次 | 0 | 0.5 秒 | 用户听后把语速定为 6.6 |
| 7（现在） | 6.6 | 每段一次 | 0 | 0.5 秒 | 待真机确认 |

- **实测语速：** 用户量了两段：34 字（含标点）4.61 秒，约 25 字 3.98 秒，合计约每秒 6.9 字。估算把标点也算字。两段差 15%，不同内容的快慢不一样，所以页面总会有一两秒偏差。
- **提前发和间隔互斥：** 下一段提前发到平台，它就连着读，段落之间没有空隙。现在估计读完才发，空隙来自这个等待。
- **这个等待同时是校准：** 声音每段都停下来等一次，估算误差不会累积。提前发的版本里声音跑在估算前面，估快了页面还会越跑越超前。
- **段落间隔的估算：** 每段多算 7 个字的时间，约 1 秒，其中 1 个字是换行。实际听到的空隙等于这个时间减去估算和实际语速的差，所以长短不一。
- **翻页时机：** 页面更新到眼镜约 2.5 秒，文字变成声音也要 2 秒左右，两边大部分抵掉，页面只需提前 0.5 秒。
- **朗读时的其他规则：** 暂停后退 20 个字，再找到句首接着读。翻到别的页再继续，就从那一页开头读。滑动翻页和语音翻页、跳章都从新位置接着读。

### 11.3 当前段落的标记

| 效果 | 结果 | 说明 |
|---|---|---|
| 缩进换成“空格加 ●” | 采用，用户的主意 | 只改文字，页面不动。`●` `○` `◆` `■` 在 16、20、24、32 号上都正好一个字宽，后面的字不动；`·` `•` `・` 宽度不对 |
| `spangroup` 分三截，中间加粗 | 模拟器可用，没采用 | 粗体和常规一样宽，文字不跳。但一行写满时 `\n` 会多空一行，要 22 字以内 |
| 浮动竖条（`top`、`height` 绑定） | 模拟器可用，没采用 | 移动时刷新 2 个绑定 |
| 下划线 | 没做 | 一句跨几行要几条线 |
| 逐字动画 | 不做 | `animate-*` 启动后没法重启，逐字发数据又有约 2.5 秒延迟 |

这本书的段落很短，按段标记基本等于按句，而且标记和朗读文字同时发，不靠估算。从段落中间接着读时没有缩进，这一段不标。

### 11.4 语音误触发丢进度

麦克风一直开着，用户说的“记录一下当前开头的这个字符”里有“开头”，被当成回到开头，进度回到了书头。`progress.json` 只存最新位置，是从控制台日志的渲染记录里找回的：`querySessionDetail` 的 `events` 里有每次发给页面的 `h`、`r`、`f`、`s` 字段。会跳走的命令现在要整句匹配。

### 11.5 眼镜重启

| 会话 | 最后一次翻页 | 翻页次数 | 自动翻页累计 | 结束时间 |
|---|---|---|---|---|
| 第一次 | 第 15.0 分钟 | 53 | 8.5 分钟 | 最后翻页后 146 秒 |
| 第二次 | 第 14.7 分钟 | 93 | 约 9.3 分钟 | 最后翻页后 76 秒 |

两次都在打开页面约 15 分钟时重启，都开着自动翻页。服务端日志没有异常，翻页就是突然停了，控制台日志看不到重启原因。另有一次会话开了 16.4 分钟，但最后一次操作在第 9.9 分钟，判断不了。还缺一个对照：关着自动翻页连续开满 16 分钟。不重启就是自动翻页的计时循环有问题，重启就和翻页无关，更可能是屏幕常亮、麦克风常开或发热。

### 11.6 延迟和保活

- **操作到页面变化约 2 秒：** 控制台日志里从 `UI 操作` 到 `屏显` 底数 0.44 秒，有时约 1.05、1.7 秒。服务端处理粗细只要约 1 毫秒。
- **底数基本是网络：** 服务端处理几乎不占时间，主要是服务器到平台这段链路的延迟和丢包。
- **根本办法是换机器：** 服务放到离平台更近的地方能省掉大部分底数和偶发的慢响应，手机到平台那段省不掉。
- **保活有效：** 页面开着时，有会话在最后一次操作后撑了 292、394 秒。页面关掉后保活不算数，会话约 120 秒后结束。

### 11.7 还没验证

- 朗读时说“暂停”能不能被识别：要看平台播报时是否继续识别。
- 朗读能连续多久，会话会不会中途结束。
- 麦克风会不会把朗读声或周围的声音当成命令。
- 菜单项“听书”在真机上的表现。自动翻页开着时开始听书，从菜单开的立刻关掉，语音开的约 1 秒内关掉，真机上还没试过。

### 11.8 代码审查和智能翻页的取舍（2026-11-01）

审查分服务端、页面、语音、共用代码四块，每条都复现或读代码核对过。确认 41 条，其中几条是不同角度看到的同一个问题；否掉 1 条；复核时补了 2 条。

| 类别 | 发现的问题 | 现在的做法 |
|---|---|---|
| 语音误触发 | 开头匹配、子串匹配：旁人说的话能换书、退出、翻几十页、改字号 | 全部整句匹配，跳得远的命令动词不能省，打开书要对上书架 |
| 听书和页面脱节 | 菜单跳章时声音不跟着走；自动翻页每次都打断朗读；摘下眼镜后还在读 | 菜单和语音走同一条路；听书时页面关掉自动翻页；摘下眼镜或 2 小时没操作就停 |
| 断线重连 | 更新没送到就记成已发，补不回来；听书时钟没重置，重连后连发几段 | 重连全量重发，听书从正在读的这段重新计时 |
| 进度和设置 | 位置被吸到页图版的页首，重开往回退；保存亮度时改掉页图版的字号；进度文件读失败后被清空 | 存文字版这一页的第一个字；没改的设置原样留着；坏文件留一份，不覆盖 |
| 大书 | 没认出章节时整本算一章，反复重排全书，超过容器 256 MB 上限 | 放宽章节识别，超大章节按段切开，内存里只留最近两本 |
| 出错 | 读书、写进度失败直接断开连接，重连后撞上同一个错 | 只发非致命的 `ERROR`，连接留着 |
| 发布 | 不跑测试，容器起不来也算成功；页图 key 会进错误日志 | 发布前跑测试，等到健康才算成功；`/r/`、`/text/r/` 的错误日志只留 crit |

- **否掉的一条：** 报告说 `{{100 - s.b}}` 常量在左算不对。反汇编内核后不成立，每段查不到变量就用 atoi，常量在左能算。误报来自旧的约束 9，它写着“常量在左得 0、除法被忽略”，和 §10.2 矛盾，`tests/test_pages.py` 还照着它加了规则。结论写错的代价和 §10.2 的“旧规则”一样，所以约束 9 现在写的是内核怎么切表达式，并注明没有实跑。
- **审查不动的：** 语速 6.6、段落间隔、页面提前 0.5 秒、`LISTEN_LEAD_SECONDS = 0` 是真机调出来的（§11.2），分区遮罩是用户定的（§10.2）。
- **按键链模拟器没做：** 现有用例已经遍历了所有状态和按键去向，再做一个模拟器没有对应的问题要抓。

智能翻页的用法在 `agent.md`，这里只记为什么这样做：

- **放在服务端：** 每页停多久要用字数除以速度，页面不知道每页多少字，表达式也只算一个运算符。服务本来就在估听书的位置，复用这个引擎改动最小。代价是要联网，所以页面本地的自动翻页留着。
- **不提前，段落间隔不算时间：** 听书要提前翻页、要等段落读完，都是为了和声音对齐。智能翻页没有声音，要的只是每页的停留时间跟字数成正比，发送延迟是常数，不影响停留时间。
- **位置只看时间：** 听书的估算不能超过已发出去的文字，智能翻页没有这个限制。按段走的话，段落短时每拍只走一段，速度被段落长度卡住：一段 7 字时每秒最多 28 字，设多快都没用。
- **圆点节流：** 只换圆点的 UPDATE 至少隔 2 秒，每段发一次太频繁。翻页不等这个间隔，所以圆点最多落后约 2 秒，页面不会晚。
- **和听书互斥，共用一个开关：** 同一个引擎分两种模式，`ls` 告诉页面当前是哪个。自动翻页的状态在页面的 `d:` 里，服务写不到，只能由页面每秒看一次 `ls`，自己关掉。

### 11.9 眼镜的真实亮度读得到吗（2026-11-01）

结论：文档里读不到，只能写。没有在真实会话上确认过，下面分开写。

### 11.10 菜单和卡顿这一轮的取舍（2026-11-01）

复核分页面状态机、服务引擎、页面和服务的约定、网络卡顿四块，每条都由另一个 agent 复现或否掉，最后再查一遍漏了什么。

| 发现 | 处理 |
|---|---|
| 菜单开着时用语音开智能翻页，页面写“已暂停”却在翻 | 服务记 `menu_open`，开着就停表 |
| 断线时滑动的上报丢了，退出、开听书都从旧的那一页算 | 每个上报带 `slot`，先跟上页面 |
| 滑动赶上服务刚翻页，多走一页 | 上报带 `v`，对不上时少走一页 |
| 翻不动时一滑全量重发一环，还会把页面刚写的 `ls`、`fs` 盖回去 | 至少隔 5 秒，不带这几个字段 |
| 开自动翻页的上报丢了，页面 `ls` 是 0，菜单停不了智能翻页 | 面板确定时重发 `ls` |
| 旧服务配新页面时一直显示“网络卡顿”，翻不动 | 只在回滚时发生，写进 `deploy/cloud/README.md`：回滚服务要连页面一起回滚 |
| 一条 UPDATE 丢了但连接没断，环上留着旧页 | 没修。这种丢失从没见过，先看调试日志，要修得加序号，见 `agent.md` |

为了省根节点，`event://go?` 并进了 `event://move?`（多一个参数 `p`），滑动事件改成 `s21a?`、`s21b?` 这样，`event://s24` 这个前缀两个方向都接得到。模拟器验证过的内核写法：`emit` 带多个参数、`{{d:a + d:b}}` 两个变量相加、前缀事件排在具体事件之后、`dataSource://update` 同一串里下一行就读得到、生命周期属性里的 `{{d:m}}` 在触发时取值。

### 11.11 查表省元素（2026-11-01）

根节点到了 64，绑定 123，再加功能就要腾地方。表达式只能有一个运算符，所以页面里很多分支只是在算一个数：下一个槽、下一个菜单项、下一档字号。这些都能换成查表。

模拟器（内核 v0.2.11）实测：

| 写法 | 结果 |
|---|---|
| `data://update?i={{nx[d:i].n}}`，元素是 `{n: 1}` | 能用，写进去是整数 |
| `dataSource://update?fs={{up[fs].n}}`，下标是主数据 | 能用 |
| `text="{{hh[d:i].n}}"` | `i` 一变就刷新，日志的 `bindings applied` 不一定算它，要看屏幕 |
| `top="{{tt[d:m].n}}"` | 能用；布局绑定，每次写数据都重新设置，隐藏时下标超出表也没报错 |
| 服务端 UPDATE 整个换数组 | 能用，当前槽立刻显示新值 |
| `{{nx[d:i]}}` 不带字段，元素是数字 | 取到的是对象 `{"value":1}`，要写 `.value`。文档没写，所以都用 `{n: 值}` |
| `{{up[fs]}}`，`up` 是对象，用数字当键 | 取到空值 |
| `{{nx[hi].r[d:i].n}}`、`{{nx[hi][d:i].n}}`，两个下标都是变量 | 取到空值或 `{}` |
| `{{nx[d:i + hx].n}}`，下标里有表达式 | 取到空值 |
| `<json>` 或 `<data>` 里的数组，下标是变量 | 取到空值，写死下标才行。所以表不能放进模板，只能由服务发 |
| `{{d:i == hi}}` 写在 URI 里 | 展开成 `true` / `false` |

**第一版错在把会变的东西放进了数组。** 页码、章节名和环的边界也查表时，根节点 53、绑定 99，但数组只能整个发，一格变了要重发八格。字号 24 时一页正文只有约 350 字节，翻页的更新从平均 420 字节涨到 751 字节，7 页一章时从 459 涨到 1049。这版没有部署。

服务端也改不了数组里的一格：UPDATE 发 `"ff[1].n"` 时，写死下标的 `{{ff[1].n}}` 看起来变了，其实这是一个名字就叫 `ff[1].n` 的字段，`{{ff[d:i].n}}` 还是旧值。`dataSource://update?ff[1].n=x` 能改一格（文档 §10.3.1），但这是页面自己写，服务用不上。`font-size` 写在父元素上也不继承，label 不写字号时什么都不显示。

现在的规则：**查表只用在不变的数据上，打开时发一次；每次翻页会变的数据仍然是单独的字段。**

| 改动 | 根节点 | 绑定 |
|---|---|---|
| 翻页的首尾循环查 `nx`、`pv`，到环的尽头还是比 `hi`、`lo` | -2 | |
| 菜单移动查 `mn`、`mp`，显示设置的单击查 `me`，主菜单第 2～4 项发 `e{{d:m}}?` | -3 | |
| 字号查 `up`、`dn` | -2 | |
| 粗细的滑动写在 `d:m == 22` 这一支，单击落到下一支 | -1 | |
| 打开页面时 `on-load` 直接写亮度，不用 `event://init?` 过一道 | -1 | |
| 菜单高亮框查 `tt`，两个菜单各一个 | | -10 |
| 章节名只留一个 label，发当前章节 `hd`，换章才发 | | -7 |

结果：根节点 64 → 55，绑定 123 → 106（模拟器日志）。翻页的更新平均 411 字节（35 页一章）、419 字节（7 页一章），比原来还少，因为章节名不用提前发。打开页面多约 1 KB，只发一次，卡顿时的全量重发不带这些表。

代价是翻过章节时章节名比正文晚约 0.5～2 秒，和百分比、进度条一样。

没动的：

- 正文也能查表，再省 30 来个绑定，但每次翻页要重发八页。
- 亮度遮罩七块是用户一档一档调出来的，合并后暗部效果可能变。

查表只在模拟器上验证过，文档里有 `list[d:selectedIndex].id` 这种写法，但真机还没跑过这些页面。

### 11.12 听书、智能翻页只补一页，智能翻页放到眼镜上（2026-11-01）

**只补一页：已做。** 原来服务改不了页面正在显示哪个槽（`i` 在 `d:` 里），听书、智能翻页、语音翻页只能留在原来的槽，把八个槽的内容都换一遍。`i` 挪到主数据后，页面用 `dataSource://` 写，服务用 UPDATE 写，和 `fs` 一样，服务翻页时只补环上新进来的一页。根节点 54，绑定 108。

模拟 375 秒，接近真书的中文正文，字号 24：

| 模式 | 翻一页，原来 | 翻一页，现在 | 总流量，原来 | 总流量，现在 |
|---|---|---|---|---|
| 智能翻页 | 3168 字节 | 551 字节 | 217 KB | 71 KB |
| 听书 | 3229 字节 | 419 字节 | 77 KB | 24 KB |
| 语音“下一页” | 约 3.2 KB | 约 430 字节 | | |

剩下的大头是段落圆点：换一次要重发两页正文，约 700 字节，智能翻页 71 KB 里占 39 KB。

槽号现在是绝对的，服务和页面都写 `i`，所以撞车要分情况：

| 情况 | 结果 |
|---|---|
| 服务翻页的更新还在路上，用户往后滑 | 页面自己走到同一格，上报的槽号和服务一样，只算翻了一页 |
| 同样的时候往前滑 | 服务走到上报的槽。页面的 `v` 是旧的，说明那条更新之后才到，服务再发一次 `i` 把页面拉回来 |
| 用户滑动，`v` 是新的 | 不发 `i`：连滑时发回去会把页面拉回来 |
| 服务翻页的更新还在路上，用户点了菜单 | 上报的 `slot` 比服务旧，`v` 也旧，不算丢了滑动，不跟 |
| 断线重连 | 没开引擎时不发 `i`：断线时滑过的话页面比服务新。引擎走着时发，位置听服务的 |

原来 `_turn` 里按 `v` 减一页的逻辑不要了：槽号不再滞后。`i` 和 `ls`、`fs`、`fw` 一样算页面自己也写的字段，卡顿时的全量重发不带。

**智能翻页放到眼镜上：做得到，不划算，没做。** 自动翻页的倒计时可以直接用，`{{wc[d:i].n / zs}}` 能算出每页停几秒（模拟器，结果取整），服务要多发一张每页字数表，每次翻页多约 70 字节。好处是不等网络，断网时也按时翻。坏处：

- 没有段落圆点：页面改不了正文的字。
- 语音停不了：`d:p` 这类状态服务写不到，和自动翻页一样。
- 两次眼镜重启都开着自动翻页，是不是页面计时引起的还没查清，同样的计时不该再多用。
- 补页还是要联网，听书也放不到眼镜上。
