# 眼镜小说阅读器：调研结论（2026-10-29）

目标：用千问 AI 眼镜 S1 的 Skill 做一个看 TXT 小说的软件——眼镜上界面好看、镜腿滑动翻页、左右侧栏显示状态 / 书名 / 操作；眼镜通过接口拿小说内容和进度；电脑端读 TXT、回传内容、记录进度。

依据：千问 AI 硬件开放平台官方文档（下称"文档 §N"）、glasscast 投屏项目在**同一块真机**上测出来的结论（glasscast 仓库的 `docs/research.md`，下称"投屏 §N"），以及本次在本地 WASM 模拟器里跑通的原型（§6）。标【真机待验证】的条目还没在眼镜上跑过。

## 0. 结论

1. **翻页不能经过大模型**。每次工具调用都要过模型（秒级），工具还有 3 s 超时、跨境链路经常超时（投屏 §9.9）。翻页必须在眼镜页面里本地完成。
2. **页面自己发不了 API 请求**。Waft-DSL "不直接 fire HTTP / RPC"（文档 §33 §5），页面里唯一能主动访问网络的是远程图片 / GIF / 帧合集的下载。所以推荐方案把**正文做成电脑端渲染的页图**：滑一下 → 页面里一个计数器加一 → 图片地址变化 → 手机替眼镜下载新的一页。电脑端从请求地址就知道用户翻到了哪一页，**进度天然被记录**，不需要另一条回传通道。
3. 两侧栏、菜单、高亮框用**原生控件**，按键立即响应，不产生网络请求；正文页图里带章节名、百分比、页码和进度条。
4. 这套方案用到的机制都已在真机上验证过（图片按地址后缀加载、换图约 1 张/秒、`data://` 改计数），**不需要白名单、不需要发布插件**就能真机测试。翻页延迟预计约 0.7～1 s（家里局域网），在外经公网约 1～1.7 s。
5. 本次在模拟器里跑通了完整原型：TXT → 分章 → 分页（禁则、悬挂标点、两端对齐）→ 4 级灰度 PNG（每页约 9 KB）→ 页面翻页 / 菜单跳章 / 改字号 → 电脑端按字符偏移记进度（§6）。
6. 想要"原生文字、瞬间翻页"，有两条升级路线（§3 方案 B、C），都卡在没验证或要白名单的环节上，列进 §7 的真机探针。

## 1. 平台约束（决定方案的硬条件）

| # | 约束 | 出处 | 对阅读器的影响 |
|---|---|---|---|
| 1 | 页面不能发 HTTP 拿 JSON；能联网的只有 `<image>` / `<gif>` / `<frame-set>` 的远程资源 | 文档 §33 §5、§36 §9 | 正文只能是图片，或在打开页面时一次性放进 dataSource |
| 2 | 页面数据只有三个来源：打开时的 dataSource、页面内 `data://`（只能写标量）、Agent 推送的 `SHOW_UI UPDATE` | 文档 §34 §4、§18 | 纯 Skill 下，换内容要么换图片地址，要么让模型重新打开页面 |
| 3 | 打开页面要由模型调 `ui_page_render`，dataSource 是模型从工具返回值里照抄的；`ui_schema.json` 的 Hook 在真机上看不到 MCP 的结构化出参（只有 `content[0].text`），条件不命中 | 投屏 §9.5 | dataSource 只放三个短字段（地址前缀、书名、显示设置），让模型抄得又快又准 |
| 4 | 工具 3000 ms 超时；平台在大陆、服务器在境外，第一次调用常超时，要"超时立刻原参数重试一次" | 文档 §40、投屏 §9.9 | 打开书、跳章这类偶发操作可以走模型；翻页不行 |
| 5 | 真机远程图由 iPhone「千问AI穿戴」App 下载再经蓝牙送到眼镜：每个文件约 0.65 s 固定开销；换图快于约每 0.7 s 一张就一张都显示不出来；地址必须以图片后缀结尾（`?ts=` 查询串下载成功但不显示） | 投屏 §9.6、§9.18～9.20、§9.25 | 翻页约 1 s 一页，阅读够用；快速连滑时只显示最后一页（位置仍然正确，见 §4.2） |
| 6 | 远程图解码预算 742 400 B；640×290 整屏图真机不显示，600×272、480×218 能显示；2.5～10 KB 都显示过 | 投屏 §9.7 | 正文图 478×290（解码 554 KB），4 级灰度 PNG 约 9 KB（最大 10 KB） |
| 7 | 内核按完整 URL 缓存远程下载，跨页面有效；真机每次绑定刷新都会让还没加载完的图重新加载 | 投屏 §9.2 E7、§9.13 | 地址里带会话号；电脑端对重复请求必须幂等（§4.2） |
| 8 | `data` 只存小整数（真机超过 2147483647 会被卡住）；`data://update` 写多个键用 `&amp;` 分隔，`on-key-*` 和 `<event action>` 在内核 v0.2.11、官方预览和真机都写全了（早先 `frame-set` 的 `on-completed` 只生效第一个） | 投屏 §9.11、§9.2 E4 | 每个操作只写一个计数器 |
| 9 | 表达式：**只算第一个运算符**（`{{d:x * 36 - 36}}` 得 `x*36`，`{{d:x + 1 + 1}}` 得 `x+1`），常量在左时算术结果为 0；除法被忽略；比较式三元结果不可靠 | 本次模拟器实测 `img/probe-arith.png`；投屏 §9.13、§9.2 E10 | 页面里算不出百分比，进度显示放进页图；高亮框用固定位置 + `a:if` |
| 10 | 按键只有 `on-key-enter/back/prev/next/home`；S1 手势：单击 = enter，双击 = back（默认退出页面），前滑 / 后滑 = prev / next | 文档 §33 §8.5、§36 §4.10；模拟器按键表 | 见 §4.3。模拟器和官方预览的按键面板把 `on-key-prev` 标成前滑，页面提示和系统提示图标（`res://prompt/slide-forward`）都写前滑下一页。2026-10-31 真机用下来页面提示没有问题，判断方向看真机，别看面板 |
| 11 | `scroll-view` / `markdown-view` / `recycle-view` 默认进焦点链，会吃掉上下键用来滚动 | 文档 §36 §12 | 阅读页不用这些组件，按键全部交给页面级 `<key-event>` |
| 12 | 屏幕是 640×290 单色绿光机：黑 = 不发光，颜色只表现为亮度；字号只有固定档位 | 文档 §34 §3、投屏 §9.2 E6 | 黑底亮字；正文用电脑端字体渲染，不受字号档位限制 |
| 13 | 每个节点直接子元素 ≤ 64、页面绑定 ≤ 128、`<tick>` ≤ 4，其余上限见 §10.1 | 文档 §35 §6、投屏 §9.8、§10.1 | 阅读页 42 个根子元素，余 22 个 |

## 2. 需求怎么落到平台上

| 需求 | 做法 |
|---|---|
| 眼镜上好看的 UI | 正文由电脑端排版渲染（字体、行距、禁则、悬挂标点、两端对齐都可控）；两侧栏和菜单用原生控件（清晰、零延迟）。截图见 §4.4 |
| 适配镜腿滑动 | 页面级 `<key-event>`：前后滑翻页、单击开菜单、菜单里滑动选择、单击确定、双击退出 |
| 左右侧栏 | 左：书名竖排 + 时间 + 连接状态；右：操作提示（阅读时）/ 菜单操作提示（菜单时） |
| 眼镜通过 API 拿小说 / 进度 | 翻页：页图地址就是 API（`GET …/r/<书>/<会话>/<计数>.png`）。打开书、跳章、查进度：语音 → 模型 → MCP 工具 |
| 电脑端读 TXT、回传、记进度 | 电脑端服务扫描书库目录、解码切章分页、按请求渲染页图；进度按字符偏移存 JSON（换字号后仍落在同一段） |

## 3. 三种方案比较

| | **A. 页图（推荐）** | B. 原生文字分段下发 | C. Agent 自定义接入 |
|---|---|---|---|
| 正文怎么到眼镜 | 页面换图片地址，手机下载电脑端渲染的页图 | 一次把约 10 页文字放进 dataSource，页面本地翻；翻完再让模型重新打开 | 自己的 WebSocket 服务推 `SHOW_UI`，收 `UI_ACTION`（镜腿事件） |
| 翻页延迟 | 约 0.7～1.7 s | 段内瞬间；每约 10 页停 3～6 s 等模型 | 每页一次云端往返（约 0.5～1.5 s，未测）；可与 B 混用做段内本地翻页 |
| 文字效果 | 电脑端字体，排版完全可控 | 眼镜原生字体，固定字号档位 | 同 B |
| 进度记录 | 页图请求本身就是进度 | 段内翻页电脑端不知道，需要另做信标图 | 服务端天然知道 |
| 前置条件 | 无（全部机制真机已验证） | 要验证：OpenAPI 工具 + Hook 能否把结构化出参交给页面；`svc://ui-action?mode=agent` 在普通 Skill 里能否触发模型 | 自定义接入白名单（联系运营）、公网 wss、插件和关联技能由用户本人发布、S1 固件 ≥ 1.11.5 |
| 主要风险 | 翻页要等约 1 s；断网时翻不了页 | 两个未验证环节；模型要正确地重新打开页面 | 白名单和发布流程；内测功能 |

建议：**先做 A**；电脑端的书库、切章、分页、进度这一层写成与传输无关的核心，B / C 以后只是在上面加一个"输出 JSON 段落"或"WebSocket 推送"的适配层。

## 4. 推荐方案（A）设计

### 4.1 链路

```
 语音「看小说 / 继续看《雾港来信》/ 跳到第三章」
        │
        ▼
 千问模型 ──调用──► reader MCP 工具（open_book / jump / list_books / reading_status）
        │                         │  返回 {"u": "https://…/r/<key>/<书>/<会话>", "t": "书名", "s": 显示设置, …}
        ▼                         │
 ui_page_render(templateName="reader", dataSource={"u", "t", "s"})   ◄── 模型照抄 u、t、s
        │
        ▼
 眼镜 reader 页面 ── 镜腿滑动 ──► data://update?a=… ──► <image src="{{u}}/a-b-j-k-z-….png">
        │                                                   │
        │                              iPhone 千问AI穿戴 App 下载（经公网隧道 / 家里局域网直连）
        │                                                   ▼
        └──────────── 显示页图 ◄──────────── Mac 上的 reader 服务：按计数差值移动位置、记进度、渲染 PNG
```

### 4.2 页图地址协议（已在模拟器跑通）

```
GET {u}/{a}-{b}-{j}-{k}-{z}-{uf}-{uw}-{ub}-{us}.png
u = https://<公网域名>/r/<随机 key>/<书 id>/<会话号>     ← open_book 每次生成新会话号
a 下一页次数  b 上一页次数  j 下一章次数  k 上一章次数  z 自动翻页次数
uf 字号  uw 粗细  ub 亮度  us 行距（0 = 这次打开还没改过）
```

- 前五段是**只增不减的累计计数**，页面每个操作只给其中一个加一（约束 8）；后四段是设置的绝对值（§5）。段数不是九的是还开着的旧页面，按旧顺序 `a-b-j-k-f-g-z` 只取翻页用的几段。
- 电脑端记住每个会话上次看到的计数，按**差值**移动阅读位置：先改字号、再跳章、最后翻页，然后返回当前页的图片。
- 为什么用累计计数而不是"命令 + 序号"：
  - 内核会重复请求同一地址（首屏连发 3 次、绑定刷新打断加载时重发，约束 7）：差值为 0，位置不动。
  - 快速连滑时中间某个地址可能根本没发出去：下一个地址里的计数已经包含了它，位置仍然对。
  - 页面不需要知道自己在第几页，跳章、改字号后页码由电脑端重新算，页面状态不会和电脑端对不上。
- 会话的第一次请求只记基线、不移动：模型重新打开页面（同一页面 `on-new-intent`）时 `<data>` 计数不归零，换了新会话号也不会被当成几十次翻页。
- 地址里的随机 key 做鉴权（眼镜发不了请求头，同 glasscast）：key 不对、书不存在、地址不合法一律同样的 404，访问日志里 key 打码。
- 后缀写 `.jpg` 时电脑端返回 JPEG，作为真机不显示 PNG 时的退路（探针 P1）。文字页用 JPEG 不划算：q40 约 21 KB，是 PNG 的两倍多。

### 4.3 交互映射

| 状态 | 前滑 / 后滑 | 单击 | 双击 |
|---|---|---|---|
| 阅读 | 下一页 / 上一页（`a`、`b` 加一） | 打开菜单 | 系统默认：退出页面（进度已在电脑端） |
| 菜单 | 上下移动选中项（到头停住） | 执行：返回阅读 / 自动翻页 / 下一章 / 上一章 / 显示设置；返回和换章执行后关菜单。自动翻页关着时这一项进设置，开着时显示“停止自动翻页”，单击直接停止并回到阅读 | 同上 |
| 自动翻页设置 | 前滑加 1 秒、后滑减 1 秒（1～30 秒，默认 7 秒，减到 1 以下显示“关闭”，此时单击不开启、回到阅读） | 确定并回到阅读 | 同上 |
| 显示设置菜单 | 移动选中项：字号、粗细、亮度、行距、返回，每项后面是当前值 | 进入这一项；“返回”回到主菜单 | 同上 |
| 调某一项 | 前滑增大、后滑减小，右栏中间显示当前值。字号、粗细、行距每滑一下就换页图，连续滑动时停手后显示最后一张；亮度是本地遮罩，立刻变 | 保存亮度并回到显示设置菜单 | 同上 |
| 任意 | 语音「跳到第 N 章」「回到开头」「换一本」「我看到哪了」 → 模型调工具 → 重新打开页面 | | |

实现要点（`pages/reader/template.xml`）：

- 菜单状态只用一个变量 `m`：0 = 阅读，1～5 = 主菜单，11～15 = 显示设置菜单，21～24 = 调字号、粗细、亮度、行距，25 = 自动翻页设置。条件全写成"变量 运算符 常量"（约束 9）。
- 按键只有一条 `<key-event>` 条件链，按状态分支，一个元素同时写单击、前滑、后滑（§10.2）。动作和关菜单写在同一次 `data://update` 里，所以不会出现“关了又开”。
- 菜单里移动选中项不改图片地址，不产生网络请求，只是原生控件重绘。
- 自动翻页的计时放在页面里，步数存在事件参数里倒数（投屏 §9.19 的探针五）：`<tick>` 只有秒、分两档且会刷新绑定，data 每写一次都可能打断图片加载，不用 tick 是因为它打开页面就一直刷新，没法随开随关。真机实测每步约 12 ms，所以 84 步约一秒；每走完一秒写一次 `c`（这一页还剩几秒），左栏显示“N 秒后翻页”（原生字号只有固定档位，15 会退回 14，所以用 14 号），到点把 `c` 和 `z` 一起写。关闭时循环不运行，页面不刷新；开启时的耗电未测。手动翻页在同一次写入里把 `c` 写回整页时长并改图片地址，菜单打开时倒计时停住、左栏显示“自动翻页 / 已暂停”，关菜单后重新计时；页面被遮挡、灭屏、摘下眼镜时关闭。`z` 的差值再大也只翻一页。新图加载约 1 秒，这期间用户看到的还是旧页，所以服务端把 1.5 秒内先后到达的一次自动翻页和一次手动“下一页”算成同一次（`TURN_MERGE_SECONDS`），连续手动翻页不受影响。
- 亮度：整屏最上面盖一层黑色，`bg-opa` 绑定 `d:op`，亮度每档差 10%、透明度差 25，正文、书名、操作栏、时间和菜单一起变暗，调的时候不用换页图。`<data>` 的属性不解析绑定，所以打开页面时用 `on-load` 把 dataSource 的 `s` 写进 `d:`；`s` 由大模型照抄，漏传时留默认值（全亮），没保存的项不会发给电脑端。
- `animate-alpha` 结束后值能保持，但 `a:if` 只是显隐，模拟器里切换后动画不会重新开始，所以不用它做“过一会变暗”。
- 数据写入和图片加载的关系（模拟器，图片 2.5 秒才返回，5/10/15 秒的累计请求）：不刷新 2/3/3；每秒写数据 2/4/5，写的键没有任何绑定也一样；`<tick>` 每秒刷新 2/4/5；`refresh="minute"` 2/4/4，但这种模式下读到的 `tick:` 值停在上次刷新时，不能当秒表。只有 `src` 里带绑定的图才会重新请求。结论：图加载完之后写一次没有代价，图没加载完时任何写入都会让它重来。
- 不禁止返回键（`forbidden="back"`）：真机上 `waft://app/exit-page` 的可靠性没验证过（投屏 §9.17），保留系统双击退出最稳。

设计取舍：

- **黑底亮字**：光机黑色不发光，大面积亮色在眼镜上是一整块亮绿（投屏 §9.20）。正文灰度 235、辅助信息 120、线条 60。正文再描粗 0.08 px、字边半透明像素乘 1.3 再量化，24 号的满亮像素从 44% 到 60% 以上，页眉页脚不变（§5）。
- **黑体而非宋体**：宋体的细横在绿色光机上可能发虚（还没在真机上对比）；Hiragino Sans GB W3 笔画均匀（对比图见 §5）。字体、字号、行距都在电脑端，可随时换。
- **进度放在页图里**：服务端掌握位置，页面算不出百分比（约束 9）。侧栏只放不随翻页变化的书名和本地就能拿到的状态。
- `theme="no-status-bar|disable-chat-bar"`、`screen-awake="keep"`：沉浸式全屏、阅读时不熄屏（`keep` 真机未验证，投屏 §8-5）。
- 不用 `<tick>` 刷新时钟：真机上图片没加载完时每次绑定刷新都会重新加载它（约束 7）。时间随每次翻页刷新，阅读时足够准。
- 可选打磨【真机待验证】：两侧栏加 `display-z="far1"`，让正文在立体视觉上更靠前（文档 §35 §3）。

### 4.5 进度

- 电脑端每次位置变化就写 `progress.json`（原子替换）：书 id → 字符偏移、字号、本章页码 / 本章页数、章节名、百分比、更新时间。
- 用**字符偏移**而不是页码保存：换字号或改版式后重新分页，仍然落在同一段文字上（模拟器验证：24 → 28 号，第二章第 1/4 页 → 同一段文字所在的第 1/5 页）。
- 只有真的移动了才写（重复请求不写）。
- 语音"我看到哪了"→ `reading_status` 工具直接读这个文件。

### 4.6 MCP 工具与 SKILL.md（`glassreader/mcp_tools.py`、`skill/SKILL.md`）

| 工具 | 入参 | 返回 | 说明 |
|---|---|---|---|
| `list_books` | `query`（可空） | 书名、读到的章节、百分比、最后阅读时间（最近读的在前，最多 20 本） | "书架里有什么" |
| `open_book` | `title`（可空 = 最近读的那本；书名号可有可无，完全相同 > 开头相同 > 包含） | `u`、`t`、章节、本章页码、百分比、字号 | 每次生成新会话号；记一次"最近阅读" |
| `jump` | `title`、`chapter`（“第三章”“3”“夜渡”“下一章”“上一章”）/ `percent` / `pages` | 同 `open_book` | 模型随后用新的 `u` 重新打开页面 |
| `reading_status` | `title`（可空） | 书名、章节、本章页码、百分比、最后阅读时间 | 不打开页面 |

- 返回体都是扁平 JSON，`message` 是可以直接念的一句话（"已打开《雾港来信》，第二章 第一封信""书架上没有找到《三体》，有：…"），技术细节在 `error`。
- 参数按宽松类型收：章节号传整数、百分比传 `"50%"` 都行（大模型常这样传）。
- 本机实测（无状态 `tools/call`，不先 `initialize`，同平台「无状态协议」）：每次 14～76 ms。

SKILL.md 要点（沿用 glasscast 已验证的写法）：

1. 用户想看小说 / 继续看 / 换书 / 跳章：先调工具，成功后**必须**调 `UI页面渲染(templateName="reader", dataSource={"u": <返回的 u>, "t": <返回的 t>, "s": <返回的 s>})`，三个字段逐字照抄。
2. 工具返回"工具调用失败 / 工具执行失败 / MCP 工具执行超时"时，不说话、原参数立刻重试一次（投屏 §9.9）。
3. 不要朗读正文；只播报一句"已打开《…》第 N 章"。（以后可加"读给我听"：工具返回当前页文字，由模型播报。）
4. 页面打开后翻页、菜单都在眼镜上完成，不需要模型参与。

## 5. 电脑端设计（`glassreader/book.py`、`pager.py`、`library.py`）

| 环节 | 做法 |
|---|---|
| 解码 | BOM（UTF-8 / UTF-16）→ 严格 UTF-8 → GB18030（国内 TXT 大多是 GBK） |
| 切章 | 正则匹配独占一行的「第…章 / 节 / 回 / 卷 / 集 / 部 / 篇」「序章 / 楔子 / 尾声 / 后记 / 番外…」，标题 ≤ 30 字；第一章前有内容就归为「前言」；一章都匹配不到就整本作为一章 |
| 段落 | 按行切段，去掉首尾空白和全角空格，段首统一缩进两格 |
| 断行 | 按实际字体逐字量宽度贪心断行；行首禁则字符（`，。、；：？！）》」』…—”` 等）悬挂到上一行行尾，最多两个；行尾禁则字符（`（《「『“` 等）推到下一行 |
| 对齐 | 非段末行逐字画、把剩余宽度均分到字间，右边缘齐整 |
| 分页 | 每页固定行数（24 px：7 行，约 110 字），章节从新页开始。**按章、按需分页**：几 MB 的长篇全书分页要好几秒，工具只给 3 s；所以页脚页码是“本章第几页”，全书位置看百分比和进度条 |
| 渲染 | 灰度画布 → 量化到 4 级灰度 → PNG。24 px 每页中位 8.4 KB、最大 9.3 KB，16 px 中位 7.6 KB、最大 11.5 KB，单页渲染约 13 ms（不量化约 24 KB、8 级约 12 KB、JPEG q40 约 21 KB） |
| 笔画 | `TEXT_STROKE` 0.08 px + `TEXT_GAIN` 1.3，用 Noto Sans CJK 在模拟绿色下对比过：描粗到 0.12 时 16、18 号的密字开始糊。真机效果还没对比。字符落点不用取整：Pillow 已经按整数像素画，取整前后输出完全相同；纯单色渲染笔画粗细不匀，不用 |
| 字号 | 16～32，每档差 2，每本书各记各的。16 号每页 10 行、每行 28 字 |
| 显示设置 | 粗细 6 档（默认第 3 档）、亮度 100%～10%（每档差 10）、行距 125%～185%（每档差 15，默认 140%）。全局一份，存在进度文件的 `_display` 键下，换书不用重调。档位都是等差的，页面上直接加减，不用查表 |
| 设置值 | 图片地址最后四段是字号、粗细、亮度、行距，0 = 这次打开还没改过。这几段是绝对值，同一个值重复出现不算操作。字号、粗细、行距滑动时就写，亮度单击保存时才写 |
| 书名 | 左栏 72×176 的小图，约 1 KB。短书名 24 号一列；长的缩小到 20～14 号排两列，“书名 - 作者”各占一列，放不下才省略。原生控件算不出字数，也拆不了列 |
| 缓存 | 字宽按字号缓存（逐字量宽度是分页的主要开销）；分页按（书、章、字号）缓存；页图按（书、字号、章、页）缓存；书文件改了（mtime 变）自动重新解析 |
| 跨章 | 翻过本章最后一页进入下一章第一页，往前翻到上一章最后一页；只有标题没有正文的章节跳过；书头书尾停住 |
| 书库 | 递归收集 `*.txt`（跳过隐藏目录）；书 id = 相对路径的哈希，改名会被当成新书 |

### 10.2 写法经验

- **一次写多个键**：`data://update?c={{d:p}}&amp;a={{d:a + 1}}` 两个键都写入，值里可以有 `{{d:a + 1}}`。文档 §36 §10.3 就是这样写的，内核 v0.2.11、官方预览、真机都成立，平台保存校验也接受。
- **旧规则为什么错了**：“每次只写一个键”来自投屏 §9.2 E4，当时测的是 `frame-set` 的 `on-completed`，后来被当成所有动作的规则，页面因此多占了二十多个根节点名额。记结论时要写清测的是哪个属性、哪个内核，换个地方用之前再测一次。
- **一条按键链**：一个 `<key-event>` 可以同时写 `on-key-enter`、`on-key-next`、`on-key-prev`，放在 `a:if` / `a:elif` / `a:else` 链里按状态分支。链是按键分开算的：某一支缺了哪个键，这个键就落到下一支，所以每支都要写全。特殊状态（如 `m == 23`）要排在 `m > 20` 前面。
- **事件也写成一条链**：`event://auto?` 用 `a:if` / `a:else` 按 `p` 定去向。拆开写时先清 `p` 会让下一条误入设置。
- **能用但没用上**：`<event>`、`<key-event>`、`<lifecycle-event>` 放在子 `view` 里也能触发，`a:if` 隐藏时也一样。文档写只能放根节点，所以只当后手。
- **不起作用**：`on-key-*` 写在 `view` 上（没有焦点）；表达式里的 `%`；条件里的 `&amp;&amp;`（只算第一个比较）；`<data>` 属性里的绑定。

### 10.4 验证方法

- **模拟器和官方预览是同一个内核**：控制台的包是 0.0.38，本地是 0.0.34，但 wasm 完全相同（sha256 前缀 `6b48dec853f0f08c`，v0.2.11）。
- **官方预览只运行已保存的文件**：编辑器里没保存的内容和“刷新”都不算。不想动草稿时，在预览页面拿到内核模块，用 `module.ccall('wasm_test_open_dsl', null, ['string','string','string'], [xml, dataJson, uri])` 注入。注入前先调 `wasm_test_close_page`，否则官方自己的页面也在跑，每个事件响应两次。
- **网页预览的局限**：不请求页图，只能看页面逻辑和写入的值；平台保存校验和真机都要另外验证。
- **保存到平台**：脚本改编辑器时，等“保存”可用再点，点到禁用的按钮不会有任何提示。保存后刷新页面，用 sha256 和本地文件比对。
- **下发到真机**：保存后的页面不用重新下发，但要退出再打开才会用上。
- **改地址格式时的部署顺序**：先服务器，后平台页面和 SKILL.md。新页面配旧服务器时，`z` 那一段会被读成字号。

### 10.5 自动翻页卡死（还没修）

- **服务端没问题**：821 个图片请求全部 200，渲染最慢 99 ms，没有重启和内存溢出，客户端地址也没变。
- **触发**：眼镜到服务器之间停 12～39 秒，没有任何请求，恢复后一批请求同时到。是蓝牙还是手机 App 还不知道。
- **为什么拖得久**：每秒写 `c` 会打断没加载完的图（§4.3 的数据），同一地址被请求 6～15 次。加载本身接近 1 秒，每秒一次写入没有余量。计时也不停，用户没看到的页被翻了过去。
- **`<tick>` 解决不了**：§4.3 的数据里，每秒 `tick` 和每秒写数据的结果一样。探针要有不刷新的基线，图片的 `src` 要带绑定，否则测不出差别。
- **候选做法**：只在最后 3 秒显示倒计时；不显示秒数；用小 GIF 倒计时（探针 8 重启过眼镜，有风险）。服务端还可以合并成批到达的自动翻页。精简版没有改这部分。
